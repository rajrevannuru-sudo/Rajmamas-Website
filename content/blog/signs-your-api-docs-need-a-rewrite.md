Most API documentation doesn't fail all at once. It drifts. A new endpoint goes in without an example, an authentication change only reaches the changelog, and a quick answer in Slack becomes the real documentation. Here are five signs it's time to stop patching and plan a rewrite.

## 1. Your engineers answer the same integration questions every week

If developers keep asking how to authenticate, which environment to use or what an error code means, the answers belong in the docs. Every repeated question is a page that's missing or hard to find.

## 2. The reference no longer matches the API

When examples return different fields from the live API, developers stop trusting the whole reference, including the parts that are still right. Docs that are generated from, or tested against, the actual API stay accurate for longer.

## 3. There's no obvious first step

New integrators need one path: get a key, make a first call, see a result. If your docs open with a long list of endpoints, people have to work out the starting point for themselves, and some won't.

## 4. Every page is structured differently

Different writers, different templates and different terms make a reference feel unreliable. A short style guide and a consistent page template fix more than any single rewrite.

## 5. Nobody owns the docs

Documentation without an owner falls behind with every release. A named owner, a simple review step in your release process and a place to log gaps keep it current.

## What to do next

Start with an audit: list what exists, compare it with the questions developers actually ask, and fix the gaps that cost the most time first. You don't have to rewrite everything at once.
